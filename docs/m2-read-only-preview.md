# M2.8 — Read-only focused tiling preview

Source implemented with deterministic tests, scoped foreground-handler acceptance, an operator-driven TextEdit menu check, and observed in-flight Pause, native desktop, and permission-loss rejection/recovery. The app can now feed real focused evidence into the pure control model and display its blocked-plan result. Production mutation scope remains empty. No enrollment, frame setters, focus/raise actions, hotkeys, or automatic polling were added.

## Use and behavior

Activate the source window, then choose **Preview focused tiling (read-only)** from the iTile menu. Each preview performs a fresh focused inspection through the existing dedicated worker and request-context guards. Pause inspections and Quit remain available. Resume requires a new read; there is no preview replay or Apply button.

The proposed single-window frame fills the sampled usable display area containing the window's center. Area selection and geometry validation are pure core logic; negative origins are preserved, boundaries are half-open, and the first matching area wins if areas overlap. There is no primary-display fallback for an offscreen center, invalid geometry, or missing usable area. Display areas are captured when the request starts; observed environment changes reject late delivery. This is a geometry proposal, not a tested frame-application policy or physical-display guarantee.

The report includes the original eligibility exclusions and unproven requirements, proposed rectangle, fixed preview block reason, and control-model rejection. It states that no window was enrolled or moved. The current assessment always supplies unknown or ineligible observations, so a fresh valid projection produces `planRejected` with `invalidPlan`. Projection, freshness, context, capability, and target failures remain distinct; a backend failure or unavailable display target cannot produce a plan.

Opening the report may activate iTile. The frontmost checks occur before presentation; return to the source window before requesting another preview or historical revalidation.

## Implemented integration boundary

`ReadOnlyPreview` owns a persistent `ControlModel` in `ITileCore`. Its owner serializes calls; the app uses its existing main-actor lifecycle for these nonblocking value reductions. It is not the proposed live control actor or synchronized setter admission mailbox. AX work remains on the platform's dedicated application threads.

The wrapper accepts `FocusedWindowEvidence`, not externally asserted eligible observations or arbitrary control events. It validates the projection and request context, reduces the observation, then reduces one explicit single-window target. It returns only fixed rejection data and the target. No `prepare`, `perform`, or `readback` effect has a platform handler. An unexpected such effect or unexpectedly admitted plan latches an internal failure, revokes the plan, and blocks further previews. Reconcile effects never dispatch automatic reads or actions in this stage.

The app and model share one authoritative environment epoch from this wrapper. Report-request counters and activation revisions stay separate. Worker tokens come from the app's existing monotonic generation issuer and attach when workers are created, before a focused read starts. Process retirement reaches the wrapper as well as the worker. Sample age uses backend start time and delivery uses the same uptime domain; the existing 0.5-second model age is still a simulation policy, not a validated live-write default.

Observed trust changes, pause/resume, desktop/display/sleep invalidation, app termination, and Quit reach the model. Request replacement and app activation revoke prior preview evidence without changing the desktop epoch or inspection pause preference. Existing request counters and activation guards discard obsolete completions before projection. Permission loss advances the model epoch; the app's report invalidation can advance it again. Epoch values are opaque monotonic generations, not counts of physical changes.

The model bounds records to 256 windows and 16 attached apps, alongside the existing one-outstanding-read-per-worker bound. [M2.9](m2-registry-lifecycle.md) now synchronizes complete worker-owned tracked sets (at most 64 tokens per worker) with each explicit reply. Missing tokens retire model records; retained older tokens can be observed after newer ones. Registry revisions and serial watermarks reject stale replacements and resurrection without an unbounded tombstone queue. Rejected observations or registry replacements do not trigger reseeding, model restarts, replacement workers, or bypasses. This explicit-read protocol does not provide continuous live enrollment or immediate owner delivery of every idle destruction notification.

## Verification and accepted scope

`scripts/format` and `scripts/verify` passed 92 tests: 81 core and 11 platform. Twelve new integration tests cover real evidence projection into blocked plans, duplicate/expired delivery, pause/resume freshness, trust epochs/recovery, desktop/activation context, request replacement, process replacement, invalid/future evidence, terminal Quit, serial ordering, display selection, and 256-record bounds.

At 2026-10-07 03:40 UTC (October 6 local), a disposable bundled debug app invoked the same foreground handlers registered by the menu through the explicit `--manual-probe` driver. An owned AppKit fixture was confirmed frontmost before every sample. Baseline and fresh recovery previews displayed the proposed area and `invalidPlan`, retained `sizeNotSettable` and all three unproven safety requirements, and issued no window actions. Pause prevented a new preview; resume obtained a fresh token at a new epoch. The fixture deliberately hid itself during an AX focused read; the app discarded the result and recovered on a subsequent fresh preview. Both test processes quit normally. Exact context and hashes are in [validation](validation.md).

The fixture sequence accepts scoped foreground-handler/report delivery. A separate operator-driven TextEdit menu action at 03:51:15 UTC produced a fresh unknown-eligibility sample, proposed frame, and blocked model plan; the user supplied its report and the same report was retrieved from the running test app. This adds scoped actual-menu/native-application acceptance. A separate synchronized preview-specific Pause check at 03:59 UTC observed Pause strictly between backend start and finish, discarded delivery, and fresh resume recovery.

The unchanged release bundle was subsequently launched through LaunchServices to test its own permission context. After refreshing its existing grant, a native desktop change at 2026-10-08 02:47 UTC produced environment invalidation and owned off-active-Space evidence inside the backend interval, followed by discarded completion and fresh recovery. Focus loss also occurred; this does not isolate a single causal guard. At 02:55 UTC, real permission switch-off produced effective trust=false and invalidation inside a delayed backend read, followed by discarded completion. Restoring the same switch recovered effective trust and a fresh blocked preview at 02:57:44 UTC. Test apps and fixtures quit normally, and the existing normal iTile instance was left running. Exact timings and scope are in [validation](validation.md).

These scoped one-display observations do not validate preview-specific in-flight display hotplug, independent-display Spaces, fullscreen, Stage Manager, lock/wake, generic lifecycle continuity, or eligible mutation. Terminal-child effective trust is not evidence of the bundle's own Accessibility grant; the permission acceptance uses the separate LaunchServices run.
