# M2.11 — Acknowledged read-only reply transport

Implemented with deterministic/barrier-controlled tests and scoped owned-window handler/Pause acceptance. This implements the read-only delivery portion of [M2.10](m2-delivery-admission.md); future semantic command buffering, synchronous write revocation stamps, and setter/action admission remain proposed. Production mutation scope remains empty.

## Implemented boundary

`ReadOnlyReceiptState` is a pure core value with idle, queued, executing, awaiting-acknowledgment, and stopped phases. Application-scoped request serials distinguish successive reads. Each read produces one terminal receipt (reply serial 1); only acknowledgment of that exact ID returns it to idle. Invalidating a read marks it canceled without releasing its occupied slot. A canceled queued read returns a canceled receipt without entering the backend. Stop is terminal, and request serial exhaustion stops rather than wraps identity.

`WindowProbe` serializes this state with its existing short mailbox lock. AX reads and registry sampling stay on the dedicated thread. Wakeups, completion callbacks, and all blocking platform calls run outside the mailbox lock. The new `inspectAcknowledged` and `inspectFocusedAcknowledged` methods deliver result, optional registry replacement, and a `ProbeReceipt`. Backend finish does not release the worker. Existing result-only/registry diagnostic methods remain available and acknowledge after their synchronous callback returns; they do not prove consumption by an asynchronously scheduled owner.

`ProbeReplyTransport` routes up to 16 registered app attachments through one shared main-actor drain chain. One reply entry remains occupied while its owner closure runs; the entry is removed by exact receipt identity before acknowledgment. Each pass consumes at most eight replies with a rotating cursor. The scheduled flag and pending entries are updated under the same lock, while scheduling, owner callbacks, and acknowledgment run outside it. A running pass can post one successor, which cannot overlap it on the serialized main actor.

Attachments use the existing monotonic process-generation issuer. Per-app request watermarks reject a receipt replay after consumption. Occupied-slot duplicates and malformed reply IDs latch a fixed protocol failure without overwriting or prematurely acknowledging the original entry. The app stops a worker whose routing fails; subsequent explicit inspection reports protocol failure. Old process callbacks cannot free a new attachment's work. Retirement/Stop disposes retained entries after their workers have been stopped; a late acknowledgment cannot revive those workers. Transport callers must preserve that stop-before-disposal order.

The app's focused inspection/preview, per-application report, and backend-only manual sample paths all use acknowledged delivery. Owner rejection, stale context, and accepted presentation return through the same automatic acknowledgment path. Pause, trust/environment report invalidation, and Quit keep their existing owner checks; report invalidation also marks occupied worker reads canceled. Canceled replies omit registry evidence rather than relabeling an old tracked set with a new epoch. Fresh inspection is required after recovery.

Active plus stopped-but-not-yet-retired physical workers count toward the app's limit of 16. Cleanup progress is checked on subsequent explicit worker creation; there is no polling or replacement of blocked threads. Registry values are checked for matching app/epoch, positive revision, legal token serials, and at most 64 tokens before delivery. Invalid replacements produce a fixed failure and no partial registry. Per-application diagnostic text retained for delivery is clipped to at most 64 KiB of UTF-8 with a truncation marker. This limits the delivered string, not raw backend construction or system allocations. Structured focused evidence uses the existing bounded summaries and projection validation.

## Verification and accepted scope

`scripts/format` and final `scripts/verify` pass 116 tests: 91 core and 25 platform. Seventeen added tests cover pure receipt occupancy/identity/invalidation/terminal stop/exhaustion; held owner consumption and exact acknowledgments using production dedicated workers; canceled queued reads without backend entry; blocked-read invalidation; oversized text and registry exclusion; 16-slot saturation and eight-reply batches; publication during consumption; a producer held at a scheduling barrier while another publishes; stale receipt/process routing; and transport Stop. Existing blocked-backend Stop tests remain passing. Fake backends do not touch real AX windows or grants.

A separate disposable bundled debug app used the ordinary foreground preview handler against an owned native-AppKit tab fixture. Retained first/second window switching and three close/recreate cycles produced fresh registry-backed blocked plans. An observed usable-area notification advanced the epoch between baseline and the first tab sample; retained-token comparisons were limited to the matching later epoch. No desktop identity or physical hotplug cause is inferred.

For a delayed preview, Pause occurred strictly between production backend start and finish. The owner discarded the late completion, retained the paused report, and a new preview after Resume recovered at a new epoch/token. All accepted previews remained `planRejected` / `invalidPlan` and retained all three unproven requirements. Both test apps exited normally; the content-free trace helper was terminated and reaped. Exact context, timings, hashes, and excluded attempt are in [validation](validation.md).

## Remaining boundary and next task

This stage does not implement the proposed 128-command semantic queue, global/per-app revocation-stamp gate, management Enable/Disable UI, keyboard commands, live coordinator, operation-ID-based setter denial event, or any AX setter/focus action. The transport bounds app reply slots and scheduling, not every possible AppKit/manual-driver input source or notification dispatch by macOS. Existing environment/report/generation counters outside the new read serial still retain their prior allocation policies. Unknown eligibility remains a control blocker.

Next: implement the bounded semantic-command and revocation boundary with pure reductions and synchronized fake-worker admission tests. Keep the app read-only while proving that older publication/Enable/Resume cannot reopen a newer revocation, overload preserves ordered command outcomes, and pre-permit denial releases only matching work. Real permission/Space/display races for this changed delivery path, idle destruction continuity, mouse movement/resizing, and eligible setter acceptance remain separate checks; historical M2.8 experiments do not newly validate this source.
